Independent Research / Developer Implementation

GitHub Apps: Installation and User Authorization

An examination of the assumptions developers can form when installing a GitHub App, configuring repository access and implementing authorization for operations performed on behalf of individual users.

Company examined
GitHub
GitHub Apps
01 / Implementation path

What we examined

This research follows a developer building an application that accesses an organization's GitHub repositories through a GitHub App.

The examination follows the implementation from app configuration and installation through authentication and resource access.

  1. Registering and configuring a GitHub App.
  2. Selecting the application's requested permissions.
  3. Installing the application on an organization.
  4. Selecting the repositories the application can access.
  5. Authenticating as the application installation.
  6. Generating and using an installation access token.
  7. Understanding when user-level authorization is required.
02 / Developer assumption

The assumption identified

Installing a GitHub App and approving its requested permissions establishes the authorization needed for the application to perform its intended operations, including actions on behalf of the installing user.

A developer following an organization-based integration could reasonably form this assumption while connecting installation, repository access and application permissions into a working authorization model.

03 / Evidence examination

Evidence reviewed

The following official GitHub documentation was examined along the implementation path. These sources establish the installation, permission and authentication behaviour relevant to the assumption.

Official GitHub documentation
  1. Installing a GitHub App from a third party

    Explains installation, repository selection and the distinction between installing an app and authorizing it to act on an individual's behalf.

  2. About using GitHub Apps

    Describes what installation grants, how repository access is selected and when additional authorization may be required.

  3. Authenticating as a GitHub App installation

    Explains installation authentication, the permissions required for resource access and the use of installation access tokens.

  4. About authentication with a GitHub App

    Distinguishes authentication as the app itself, as an app installation and on behalf of an individual user.

  5. Generating a user access token for a GitHub App

    Explains user-level access tokens and how the permissions of the application and individual user constrain the resources and operations available.

  6. Choosing permissions for a GitHub App

    Explains the different permission categories and how installation permissions differ from account permissions requiring user authorization.

  7. Generating an installation access token

    Describes how installation access tokens are generated and how their access is constrained by the installation and its permissions.

04 / Documented distinction

What the documentation establishes

GitHub distinguishes between application installation and user authorization.

Installation access allows a GitHub App to access resources available to its installation, subject to the permissions granted and the repositories selected. Requests made using an installation access token are attributed to the application.

User authorization establishes a separate authorization relationship that allows the application to make requests on behalf of an individual user. Those requests use a user access token and are constrained by the permissions available to both the application and the user.

GitHub explicitly documents that an application can be installed without being authorized, and authorized without being installed.

05 / Potential consequences

Why this matters to implementation

An application that requires user-attributed operations may need a separate user authorization flow beyond organization installation.

If an implementation treats installation access and user authorization as interchangeable, the application may lack the authorization context required for its intended functionality.

  • Additional authorization work during integration.
  • Unexpected implementation behaviour when an operation requires user-level authorization.
  • Additional debugging to identify the authorization context required by an operation.
  • More developer support requests during integration and troubleshooting.
  • Additional engineering time spent resolving authorization-related implementation issues.
06 / Business relevance

Why product teams should care

Authorization assumptions can influence how developers design integrations, structure authentication flows and allocate responsibility between their application and the underlying platform.

When an implementation assumption differs from the authorization model required by the product, the consequences can extend beyond the initial integration.

Additional implementation work, debugging and support requests can consume engineering resources and introduce friction into developer adoption.

Understanding where these assumptions can emerge gives product and engineering teams an opportunity to examine their implementation experience from the developer's perspective.

07 / Research scope

Scope and independence

This research is based on publicly available GitHub documentation and implementation guidance. It examines a defined developer implementation path and identifies assumptions that may emerge from the material reviewed. No live API calls, SDK execution or production testing were performed.
